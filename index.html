01 Built

University project

Multi-Model Blood Bank

Oracle PL/SQL · MongoDB · Neo4j · Python · pytest

[REPO LINK]

The need
A regional blood bank brief covers three kinds of data: structured stock, irregular cold-chain readings, and road routes between centres and hospitals.
What I did
I gave each kind of data the database that suits it: 8 Oracle tables with views, triggers and a package; 50 MongoDB documents; and a Neo4j graph with 7 Cypher queries. One Python desktop app connects all three, covered by 3 pytest integration tests.
Result
Neo4j answered the connected-data query in 22 ms against Oracle's 132 ms. MongoDB ran the aggregation in 17 ms against Oracle's 101 ms.
Limit
These timings come from a small dataset and a few runs, and each engine ran a comparable workload rather than an identical query. Concurrency is untested. Shortest path counts hops, not kilometres.
02 Deployed

University project · Deployed to a live AWS account for coursework

HTUNews on AWS and HealthBooking Serverless

EC2 · ALB · Auto Scaling · S3 · IAM · Route 53 · ACM · Lambda · API Gateway · DynamoDB · Amplify · CloudWatch

[REPO LINK] [LIVE DEMO LINK IF RUNNING]

The need
Two scenarios: move a news site to secure, scalable cloud infrastructure, and launch a serverless medical appointment system.
What I did
For HTUNews I built a load-balanced Auto Scaling group across 3 Availability Zones, with IAM groups, MFA, chained security groups and HTTPS. For HealthBooking I connected a Vue front end to five Python Lambdas and two DynamoDB tables, with a least-privilege IAM role.
Result
HTUNews scales from 2 to 10 instances at a 60% CPU target, with weighted routing to move traffic in four steps. HealthBooking resets slots and appointments at midnight Amman time through EventBridge, sends notifications through SNS and reports through a CloudWatch dashboard.
Limit
HTUNews is an assignment scenario, not a client. I declared AI-assistant support in my report, deployed the services myself and can explain each decision.
03 Design only

University project

Blood Hub Donation System

Feasibility analysis · Use cases · DFDs · ERD · UML · Wireframes · Traceability

[CASE STUDY PDF]

The need
Blood donation coordination in Jordan leans on manual processes and social media appeals, with no central view of available donors.
What I did
I ran a feasibility study and risk assessment, then wrote 10 functional and 7 non-functional requirements. I added 6 user stories with Given-When-Then criteria, full analysis models and wireframes, and considered Jordan's data protection law (PDPL 24/2023) and SANAD integration.
Result
A “conditionally feasible” verdict and a traceable design pack, with a hybrid Waterfall and Scrum delivery approach.
Limit
This is a proposed design based on desk research. It has not been built or tested with donors or hospitals.
04 Prototype

University project

Karaz

Figma · Personas · Segmentation · Value Proposition Canvas

[FIGMA VIEW LINK]

The need
People with allergies, intolerances or insulin resistance need a quick way to check whether a food suits them.
What I did
I defined the audience with a persona and a Value Proposition Canvas, then evolved the app from low-fidelity sketches to a high-fidelity Figma prototype.
Result
Feedback changed the product. A doctor's input removed AI medicine analysis, and friends and family replaced meal-by-meal logging with one daily log.
Limit
Karaz is a prototype, not a released app, and the feedback came from a small group.
05 Built (no-code)

University project

Jawlatuna

Adalo · SRS · SDS · Functional specification · Traceability matrix

[CASE STUDY PDF]

The need
A tourism booking idea needed proof of demand and a disciplined route from requirements to testing.
What I did
I surveyed potential users, assessed feasibility including legal issues, and followed an incremental model. I built the app in Adalo and traced 7 functional requirements through a matrix to 10 test cases.
Result
Testing logged 2 defects, and both were resolved.
Limit
The survey sample was small, and the no-code build is a working proof of concept rather than a production system.
06 Built

University project

“I report what the evidence shows.”

Emergency Response Analytics

Python · scikit-learn · PyGAD · SciPy · Jupyter

[NOTEBOOK LINK]

The need
An emergency-centre scenario asked whether response time could be predicted from operational data.
What I did
I sampled 5,000 incidents from 368,000 rows, then compared two feature selection methods and three regression models. I also built a constrained genetic algorithm that produces a readable weighted formula, and checked it with SciPy.
Result
All three models scored R² near zero, with an average error of about 4 minutes. I reported that the fields held no usable signal, and recommended planning around the stable 15-minute average while collecting richer data.
Limit
The genetic algorithm's target was built from its four input fields. It shows constrained optimisation working, not forecast accuracy on real response times.
